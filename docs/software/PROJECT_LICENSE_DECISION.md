# 项目自有代码许可证决策单

> 状态：等待项目负责人、团队和指导教师确认
>
> 适用对象：本团队独立编写的源代码与文档；不改变论文、作者代码、第三方依赖和外部数据各自的版权或许可证。

## 结论先行

若团队准备保持 GitHub 仓库公开，并允许他人复用本软件，建议项目自有代码采用 **MIT License**。它与当前候选包中以 MIT、BSD 等宽松许可证为主的第三方组件分发方式相容，文本短，答辩时也容易说明。该建议不是法律意见，且只有在团队确认代码权属与公开发布权限后才能执行。

若团队只想把软件用于校内结项、暂不授权他人复制和修改，则继续不添加项目许可证，但应把仓库或发布范围限制在团队认可的对象内，并明确写作“内部结项候选”，不能称为开源软件。

## 当前事实

- 仓库根目录没有 `LICENSE`、`LICENSE.txt` 或 `LICENSE.md`；README 已明确记载“项目自身代码的许可证尚待团队确定”。
- GitHub 官方说明指出：不选择许可证时，默认版权规则适用，他人原则上不能复制、分发或创作衍生作品；公开可见不等于开源。
- MIT 是宽松许可证，允许商业使用、修改、分发和私人使用，主要条件是随许可材料保留版权与许可证声明，并包含免责与无担保条款。
- `docs/software/THIRD_PARTY_DISTRIBUTION_AUDIT.md` 和候选包的 SBOM/许可原文已经处理第三方组件边界，但它们不授予本项目自有代码的许可。

官方依据：

- [GitHub Docs：Licensing a repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)
- [Choose a License：MIT License](https://choosealicense.com/licenses/mit/)

## 需要人工确认的三项事实

1. 项目申报书、学校规定或指导教师是否对学生创新项目成果权属、公开发布或署名另有要求；
2. 团队成员是否一致同意以开源方式授权各自贡献，并确定许可证版权行使用个人姓名、团队名称还是其他经确认主体；
3. 论文 PDF、第三方源码、MATLAB/Simulink 模型和本地研究归档是否继续排除在公共发布范围之外。

这些事项会改变公开分发边界，Codex 不代替团队作出决定。

## 备选方案

| 方案 | 适用情形 | 他人权利 | 团队义务与代价 | 本项目建议 |
|---|---|---|---|---|
| MIT | 希望公开、便于复用和协作 | 可使用、修改和分发 | 保留版权与许可证声明；不提供担保 | **优先建议** |
| 暂不授权 | 仅用于内部结项，权属尚未确认 | 默认版权限制 | 不能称开源；公共仓库和包分发边界需更谨慎 | 权属未确认时采用 |
| Apache-2.0 | 团队明确需要专利授权条款 | 可使用、修改和分发，并含明确专利授权 | 文本和 NOTICE 管理更复杂 | 当前没有必要主动增加复杂度 |

GPL 等强互惠许可证会显著改变衍生作品的分发义务；当前项目没有提出这类目标，不作为默认方案。

## 团队确认格式

负责人只需给出以下两种确认之一，并补全方括号内容：

```text
同意将团队自有代码按 MIT License 发布；版权主体写为：[经团队确认的名称]；年份写为：2026。论文、第三方仓库、MATLAB/Simulink 外部模型和本地研究归档不随之重新授权。
```

或：

```text
暂不为项目自有代码添加开源许可证；当前只作为校内结项候选使用，不制作公共正式发行版。
```

## 确认后的自动执行步骤

若选择 MIT：

1. 在仓库根目录加入标准 `LICENSE`，并在 README 标明项目自有代码许可证与第三方边界；
2. 将项目许可证纳入发布包清单，保留现有第三方许可原文和 SBOM；
3. 更新发布审计、验收说明和完成性审计；
4. 从新的干净提交重建候选包，重新核对文件清单、ZIP SHA-256、本机整包功能和合格异机证据；
5. 只有团队另行确认后，才建立正式标签或对外发布。

若选择暂不授权：

1. 保持 README 的当前声明；
2. 将发布包继续标记为“内部结项候选”，不得使用“开源发行版”等表述；
3. 不因仓库可见或第三方组件具有开源许可证而推断团队代码已获授权。
