# 项目执行、版本演进与并行协作治理规范

> 适用对象：天津市市级大学生创新训练项目“构网型变流器稳定性分析”团队
> 文档状态：执行基线，随学院通知和指导教师意见更新
> 建立日期：2026-07-16
> 最后更新：2026-08-10
> 当前研究分支：`research/nontrivial-core`；软件原型审计基线：`8934ab9`
> 管理目标：保证研究工作由本科生团队实际理解、实际执行并能够在中期检查和结项答辩中独立说明；人工智能仅作为检索、编程、审查和测试辅助工具。

## 1. 项目身份与执行边界

本项目是天津大学本科生承担的天津市市级大学生创新训练项目，不以形成完整科研产品或追求名义上的“高难度”为目的，而以完成一次规范、可复核的研究训练为根本要求。判断一项工作是否应当纳入主线，依次考察：

1. 是否服务于申报课题所涉及的构网型变流器稳定性问题；
2. 是否能由团队成员理解其理论依据、实现过程和适用范围；
3. 是否能形成可复现的代码、模型、数据或分析证据；
4. 是否能在中期或结项答辩中由学生本人说明；
5. 是否在现有时间、软件条件和本科生研究能力范围内可以可靠完成。

下列做法不计为本项目的实质成果：仅运行作者脚本而不解释输入输出；仅展示人工智能生成的文字或图表而无原始记录；将充分条件表述为必要条件；将第三方代码或论文结论表述为团队原创；以功能数量代替研究问题的论证。

项目主线保持为三个相互衔接的问题：复矩阵数值域扇形性的可靠数值判定；构网型变流器小信号导纳模型的统一表述；小增益—小相位充分条件与闭环实际稳定性的比较验证。便携式本地网页工作台已经确定为结项交付形式，但界面必须调用可测试的计算内核，不得以人工经验曲线代替研究结果。大规模开关模型、任意控制器自动建模、一般性新定理和自动优化均为非必要扩展，不得占用结项主线所需资源。

## 3. 中央判断处理机制

### 3.1 主任务的职责

Codex 主任务作为中央判断处理器，但不替代项目负责人、指导教师和学院的决定。其职责限于：

1. 维护研究问题、当前事实、版本状态和待确认事项的一致性；
2. 判断任务是否应进入主线、能否并行、需要何种证据和测试；
3. 为子任务划定文件所有权、输入、输出、停止条件和验收门；
4. 审查子任务产物，解决相互矛盾的结论，统一术语和坐标约定；
5. 运行或复核集成测试，决定是否提交本地 Git；
6. 将需要团队或指导教师作出的学术、行政决定明确列出，不越权代决。

每项工作进入执行前，主任务应建立最小“任务卡”，至少包括：研究问题、已知输入、预期产物、允许修改的文件、验证方法、停止条件和风险。缺少其中任一项时，优先补齐任务定义，不应直接生成大批代码或文档。

### 3.2 主任务的判断顺序

主任务按下列顺序处理新任务：

1. **身份审查**：是否属于本科大创主线，学生是否能在答辩中说明；
2. **事实审查**：输入、论文版本、代码版本、模型约定是否已经固定；
3. **价值审查**：是否能够增加理论解释、实验可信度或结项证据；
4. **可分解性审查**：能否划分为互不覆盖的文件和独立验收结果；
5. **验证审查**：是否存在可执行的测试、复现实验或权威来源核验；
6. **资源审查**：是否会因 MCP、外部下载、长时间仿真或许可证问题阻塞主线；
7. **提交审查**：产物是否达到单一、可验证的提交主题。

任何任务若不能形成可验证输出，或需要学生无法解释的复杂系统，应先缩小范围。任何稳定性结论若只有单一数值判据，不得进入正式成果。

## 4. 子代理的启用条件与组织方式

### 4.1 适合并行的情形

同时启用多个子代理，必须满足以下全部条件：

- 子任务之间不存在前置结果依赖，能够在同一时间独立推进；
- 每个子任务有明确、互不重叠的文件所有权；
- 每个子任务均能提供独立的来源、测试或复现证据；
- 主任务能够在并行结束后完成统一审查，而不是直接拼接结论；
- 并行能缩短等待时间，且不会增加 MATLAB 会话、上游目录或 Git 索引的写入冲突。

适合并行的典型组合是：一名子代理核对论文定义与版本差异，一名子代理审查数学算法和反例，一名子代理设计 MATLAB 测试；又如在模型接口冻结后，一名子代理准备模型说明，一名子代理准备闭环极点验证，一名子代理整理行政材料。调研与计算可以并行，但不得由多个代理同时修改同一个核心函数、同一个 Simulink 模型或同一份计划文件。

### 4.2 不适合并行的情形

出现以下任一情形时只保留主任务串行执行：

- 论文版本、dq 坐标方向、功率正方向或模型输入输出尚未冻结；
- 后一任务必须依赖前一任务生成的矩阵、模型或参数；
- 需要操作同一 MATLAB 共享会话、同一 Simulink 模型或同一 Git 暂存区；
- 当前问题属于短小定位、单文件修复或一次测试，创建子代理的协调成本更高；
- 结论涉及指导教师意图、学院通知或项目范围变更，需要人类确认；
- MCP 已出现卡顿且命令行有更短的可验证路径。

MCP 是执行接口，不是研究方法。连续 60 秒无可观察进展时，主任务应停止该调用，改用 MATLAB `-batch`、官方文档或本地文件检查；不得让某个子代理因 MCP 卡顿长期占用并行名额。

### 4.3 建议的独立工作流

| 工作流 | 进入条件 | 允许产物 | 退出条件 |
|---|---|---|---|
| 文献与版本审查 | 指定论文、仓库或工具及待核问题 | `references/SOURCES.md` 的候选更新、版本差异报告 | 给出版本、来源、校验值、许可证和未确认项；不得仅给搜索摘要 |
| 数学与算法审查 | 算法接口已定义，待验证性质明确 | 反例、证明草稿、测试建议；必要时代码变更由主任务另行分配 | 至少提供解析例或独立数值核验，并说明结论适用范围 |
| MATLAB 测试与复现 | 输入文件、运行命令和期望现象明确 | `tests/`、`experiments/`、`results/test-reports/` 中指定文件 | 从干净会话运行，报告版本、命令、通过/失败数和输出位置 |
| 模型与闭环验证 | dq、功率方向、基值、工作点和接口均已冻结 | `models/`、模型测试和精选结果 | 模型可线性化；频域判据至少由闭环极点或时域响应之一复核 |
| 行政与答辩证据 | 指定项目批次和学院 | 待确认清单、材料映射、答辩演练清单 | 区分正式通知、历史案例和团队内部标准，不推定缺失规则 |

子代理完成时必须交付四项内容：实际修改文件；运行过的验证命令及结果；仍未解决的问题；建议主任务是否接纳。子代理不得自行提交 Git、创建远端、推送、修改第三方快照或宣布阶段验收通过。

| 文件或目录 | 主要所有者 | 并行写入规则 |
|---|---|---|

| `tests/` | 测试工作流 | 可与 `src/` 分离，但测试接口须事先冻结 |
| `models/` | 模型工作流 | 同一 `.slx` 文件禁止并行编辑；模型变更后必须重新线性化和仿真 |
| `experiments/` | 集成复现工作流 | 一个入口脚本同一时刻只允许一个写入者 |
| `backend/domain/` | Python 便携数值内核工作流 | 模型 schema 与数值函数的接口先冻结；核心函数和对应测试同步交付 |
| `backend/api/`、`backend/tests/` | API 与集成测试工作流 | 不在 API 层重复实现数值公式；必须保留来源、原因码和证据等级 |
| `apps/web/` | 前端工作流 | 只消费已冻结的 API 数据契约；不在前端隐藏稳定性判定公式 |
| `scripts/`、`启动平台.bat` | 发布与运行工作流 | 开发态与发布态入口分层；改动后必须做健康检查和退出清理测试 |
| `results/` | 产生结果的工作流 | 仅提交精选结果和元数据；大体积原始输出保留本地 |
| `notes/PROJECT_LOG.md` | 主任务 | 子代理报告由主任务核验后摘要写入，不粘贴原始会话 |
| Git 暂存区、提交和标签 | 主任务 | 子代理不得执行 `git add`、`commit`、`tag` 或 `push` |

如发生文件所有权冲突，后启动的任务停止写入并转为只读审查。主任务不得以覆盖文件的方式解决冲突，应先比较变更及其测试证据。

## 6. 测试门与证据门

### 6.1 四级测试门

1. **单元门**：解析矩阵、错误输入、尺度与旋转不变性等类式测试全部通过；修复缺陷时先建立能够复现缺陷的测试。
2. **回归门**：作者代码、论文 v2 的关键频点与团队算法有固定输入快照；任何差异均能追溯到定义、版本、容差或采样设置。
3. **集成门**：从模型或频率响应数据输入到扇形性、增益/相位判据输出可由一个入口脚本完成，且不依赖工作区残留。
4. **结论门**：主要稳定性结论至少由两种独立证据支持，其中必须包括闭环特征根或时域仿真；充分条件未满足时只报告“未由该判据认证”，不得报告“不稳定”。

### 6.2 每项成果的最小证据包

每幅正式图、每张表和每项答辩结论应能够追溯到：输入或模型版本、参数与单位、运行命令、MATLAB/工具箱版本、代码提交、生成时间、原始或中间数据位置、判定容差以及已知局限。第三方图表不得改名后当作团队结果；团队复现图应注明“依据作者代码复现”，团队算法产生的增量结果应单独标明。

中期和结项演示均采用“双路径”准备：现场运行的一键脚本，以及同一提交生成的静态 PDF/图片和测试报告。演示成功不能替代测试通过，测试通过也不能替代对物理意义的解释。

### 6.3 当前已达到的证据门（2026-08-10 审计）

- 单元门：MATLAB 最新仓库记录为 128 Passed、0 Failed、0 Incomplete；Python 当前测试集为 62 项；两组数字分别描述两条测试链，不能相加或互相替代；
- 回归门：Fig. 8 `D=0.05/0.5` 原始频响和闭环谱夹具已固化，Python 便携内核在固定 1000 点网格分别得到 75/0 个未覆盖点，并由回归测试约束；
- 集成门：前后端已接入 Fig. 8 Python 内核和独立低频降阶模型，支持可编辑网络、案例 JSON 往返、结果/极点/响应/扫描 CSV、双打印式 HTML 报告和 D–X 扫描；浏览器端到端流程已覆盖核心路径；
- 结论门：Fig. 8 的稳定/失稳属性有有限网格判据与闭环极点交叉证据；作者同一模型的 176 点参数域已经完成有限网格判据覆盖区—闭环参考稳定区比较；独立模型已有同一线性状态矩阵下的极点—响应一致性核查。连续全频定理、完整平均值 `dq` 与可信非线性时域尚未完成，因此不得把阶段性结果扩大为一般结论；
- 发布门：Windows `v0.3.0-rc5` `onedir` 候选包从当前干净冻结提交构建；包内一键验收逐文件核对哈希，并检查静态前端/API、Fig. 8、同域对照、独立模型、打印报告和端口释放，生成机器可读证据；构建还会从实际可执行文件和网页生产依赖生成第三方组件清单及许可原文。回传后由项目侧工具再次核对原始 ZIP 哈希、提交号和全部冻结计数；人工浏览器导出确认仍是独立验收门。另一台无开发环境电脑的断网执行仍待人工，发布链继续标记为“在建”。

队友或人工智能提供的聊天摘要，即使与已知数字一致，也只能记为外部复核线索。只有当原始输出、运行命令、环境和代码版本进入可追溯记录，或由正式仓库重算后，才能升级为项目验证证据。

## 7. Git 提交与审查规则

当前项目已经建立 Git 仓库，初始可复现基线为 `eb506a8`，当前研究分支为 `research/nontrivial-core`，已配置已授权 GitHub 远程 `origin`。后续遵循以下规则：

1. 主任务在接纳子任务前检查 `git status --short`，区分用户已有改动和本轮改动；
2. 一个提交只处理一个可验证主题，例如“增加论文基线复现实验”或“增加边界频点回归测试”；
3. 提交前运行与变更相称的测试，并将命令与结果写入提交说明或项目日志；
4. 核心算法提交必须同时包含测试；模型提交必须包含参数说明和至少一次成功仿真记录；文献版本提交必须包含来源和校验信息；
5. 不提交密钥、身份凭证、MATLAB 缓存、Simulink 缓存、第三方 `.git`、临时 TeX 文件和无关大文件；
6. 不修改历史提交以掩盖失败实验；修正以新的、可解释的提交完成；
7. 阶段标签只能在相应验收门全部通过后由主任务创建，不以“代码看起来完成”代替验收。

建议阶段标签使用 `v0.1.0-midterm` 和 `v0.2.0-final`。标签建立前生成成果清单和 SHA-256；常规研究提交可推送到已授权远程，公开仓库、发布包和标签仍须由项目负责人确认许可证与第三方分发边界。

### 8.4 上游版本更迭处理

论文新版本、作者仓库新标签、Simplus 更新、MATLAB 或 MCP 升级均不得直接进入已验证环境。主任务应建立版本比较任务，依次核对：来源真实性、版本号与提交、许可证、接口变化、基线结果差异、测试结果和回退方式。只有新版本解决当前明确问题且全部回归测试通过，才允许更新主线；否则保持固定基线，并将新版本列为后续研究。

MCP 版本变化只影响执行方式，不应改变研究结论。若 MCP 与 MATLAB 命令行得到不同结果，以相同脚本、相同 MATLAB 版本和相同输入重新运行并比较；不得把 MCP 输出本身当作可引用的学术证据。

## 9. 人工智能使用与学生责任

人工智能可以承担资料初筛、代码草拟、反例搜索、测试生成、格式检查和并行审查，但每项材料进入答辩或报告前必须由团队成员完成以下复核：

- 阅读所引用论文或官方材料的原文，而不是只阅读人工智能摘要；
- 能解释公式、程序接口、坐标约定、参数单位和图表含义；
- 实际运行代码或模型，并保存可复核的命令和结果；
- 识别复用内容、人工智能辅助内容和团队新增内容的边界；
- 对最终结论、署名、提交和现场答辩承担责任。

人工智能生成但未经核验的申报安排、导师转写、实验数据和学术结论均视为待确认材料。任何成员若不能独立说明某段核心代码或某项结论，该内容不得作为其个人贡献，也不应成为答辩的唯一支撑。

## 10. 当前立即执行的治理决定

1. M0、M1、M2 低频首版、M3 同域对照首轮和 M4 首版已经完成；当前主线收敛 M5 发布、测试和结项材料，界面扩展仍不得超前于计算内核验证。
2. `0.578 Hz` 与论文正文 `1.2 Hz` 的差异继续作为定量待闭合项，但不改变已复现的极点实部符号和受控判据回归，因而不阻断 M1—M5。在差异闭合前，禁止声称振荡频率定量复现完成。
3. Simplus 自动生成非线性模型的近奇异与异常初始化现象采用有时限的兼容性支线排查，不再占用结项主线；其完整因果解释尚未建立，不直接定性为工具缺陷。当前低频降阶模型已经完成线性响应与极点一致性核查，但可信非线性时域参照仍待完成。
4. 队友本地聊天摘要与未进入正式仓库的 CSV/模型只登记为外部复核线索；不粘贴原始会话，不写成已验证数据。
5. M0—M4 的常规实现、测试、日志和语义提交默认连续执行，不逐项等待用户批准。需要人工介入的节点仅限于：学院正式通知与表格、指导教师范围确认、许可证与公开分发、队友异机运行、最终五分钟演示审看、签字与系统提交。
6. 主任务在子代理返回后先进行冲突审查和测试，再决定后续提交；子代理返回不等于成果被接纳。
